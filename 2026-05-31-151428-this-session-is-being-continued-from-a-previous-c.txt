  1. Core Purpose (per hub)

  Food Hub (src/app/api/marketplace, src/app/api/orders, src/app/api/groups): A
  verified agricultural marketplace for Kenyan farmers to list produce, buyers
  to purchase with M-Pesa STK Push, cooperative groups to make bulk input
  purchases from verified suppliers, price intelligence with market benchmarks,
  and an AI farm assistant.

  Education Hub (src/app/api/education, src/app/api/mentor,
  src/app/api/lecturer, src/app/api/peer-reviews, src/app/api/students): A
  structured project engagement platform for CS students in Kenya. Students
  generate AI project briefs (AI_BRIEF or OPEN_SOURCE track), submit process
  documents, go through peer review then lecturer review, and build a verified
  portfolio.

  2. User Roles

  Role enum (src/types/index.ts:4–10)

  FARMER, BUYER, STUDENT, LECTURER, ADMIN

  RBAC middleware (src/middleware.ts)

  Runs on /dashboard/:path* and /api/admin/:path*. Route prefix → role mapping:
  - /dashboard/farmer → FARMER
  - /dashboard/buyer → BUYER
  - /dashboard/student → STUDENT
  - /dashboard/lecturer → LECTURER
  - /dashboard/admin → ADMIN
  - /api/admin → ADMIN

  The middleware only handles dashboard and API admin routes. Other API routes
  (/api/marketplace, /api/orders, etc.) rely on requireRole() called inside each
  handler.

  7. Trust and Verification Systems

  Farmer Trust Score (src/lib/trust/farmerTrustCalculator.ts)

  Full 4-component algorithm: verification (40pts) + transaction (25pts) +
  rating (20pts, requires ≥3 ratings) + reliability (15pts). Triggered by order
  completion, rating submission, and farmer verification approval. Tiers at
  0/40/60/80 boundaries.

  Gap: disputesRuledAgainst always equals disputeCount because no dispute
  resolution workflow exists — every flagged dispute counts against reliability.

  Farmer Identity Verification

  Self-service document submission → admin paginated queue → APPROVED/REJECTED.
  Documents must be Cloudinary URLs. Cannot re-submit if PENDING; cannot submit
  if APPROVED.

  Supplier Verification

  Admin-only PENDING → VERIFIED/SUSPENDED. No self-registration endpoint.

  Lecturer Verification

  Admin sets lecturerData.isVerified = true via admin/verify-lecturer.
  Unverified lecturers get 403 on all lecturer routes.

  Project Verification Audit Log

  Append-only VerificationAuditLog written on every lecturer decision — records
  document hashes, GitHub snapshot (currently always zeros), review scores. No
  update or delete endpoint.

  9. Payment Architecture

  Single flow: M-Pesa STK Push (Lipa Na M-Pesa)

  1. Buyer POSTs /api/orders → atomic inventory reservation (findOneAndUpdate +
  $gte filter)
  2. initiateSTKPush called → OAuth token fetched (55-min cache) → STK Push to
  Safaricom
  3. Order created: PENDING_PAYMENT / AWAITING_PAYMENT; mpesaCheckoutRequestId
  saved
  4. Safaricom calls POST /api/webhooks/daraja?secret=WEBHOOK_SECRET
  5. Webhook validates secret → Zod schema → locates order by CheckoutRequestID
  6. On success: order → PAID / IN_FULFILLMENT; mpesaTransactionId saved (sparse
  unique index for idempotency); SMS to both parties
  7. On failure: order → FAILED; inventory restored
  8. Buyer polls GET /api/orders/[id]/payment-status

  Group orders: participatingMembers[].paymentStatus field exists but no STK
  Push is triggered. Members are marked PENDING only — payment is not collected.

  Sandbox vs production: NODE_ENV !== 'production' check in darajaService.ts.

  13. Hidden Capabilities (in code, not prominently documented)

  1. Atomic inventory compare-and-swap (orders/route.ts:234–256):
  findOneAndUpdate with $gte filter on quantityAvailable — prevents overselling
  under concurrent load.
  2. Constant-time timing protection (auth/options.ts:68–70): bcrypt compare is
  always performed even for missing users, preventing timing-based user
  enumeration.
  3. 5-effect trigger chain on RECEIVED (orders/[id]/status/route.ts:110–185):
  PriceHistory, TrustScore recalculation, PriceAlert check + SMS — all
  non-blocking and independently fault-tolerant.
  4. Counter-based order reference IDs (lib/foodhub/orderUtils.ts): Atomic
  MongoDB $inc on Counter document generates gap-free UMJ-YYYY-XXXXXX IDs.
  5. Peer review double-submit atomic guard
  (education/engagements/[id]/submit/route.ts:92–106): Creates PeerReview first,
  then uses status-guarded findOneAndUpdate; on race condition deletes orphaned
  PeerReview and surfaces 409.
  6. SHA-256 document hashing
  (education/engagements/[id]/documents/route.ts:75): Every process document is
  hashed on submission and recorded in VerificationAuditLog for tamper
  detection.
  7. LecturerEffectiveness auto-upsert (lecturer/reviews/route.ts:200–204):
  Running stats record upserted on every review — no separate initialization
  endpoint needed.
  8. ISR on knowledge routes (knowledge/articles/route.ts:17): export const 
  revalidate = 3600 — cached 1 hour, no auth required.
  9. Middleman benchmark prices (priceDataService.ts:94–105): Hardcoded
  reference prices for 10 Kenyan crops (Wakulima Market sourced) used to compute
  platform premium %.
  10. Vercel cron configuration (vercel.json): 4 cron jobs: cleanup (02:00 UTC
  daily), impact (every hour), market-insight (06:00 UTC daily),
  price-alert-check (every 2 hours).
