# WEBSITE PURPOSE V1
**Status:** Governing document. Replaces all prior website strategy documents.
**Scope:** Purpose, boundaries, principles, and audience definitions only. No design. No implementation. No UI. No visual system.
**Authority:** Every future website decision — every page, every paragraph, every CTA, every diagram, every section — is measured against this document first.

---

## WHY THE WEBSITE EXISTS

UmojaHub operates in an environment where trust cannot be assumed. The platform's core audiences — smallholder Kenyan farmers, computer science students from institutions without global brand recognition, buyers with no prior relationship to the farmer they are considering purchasing from, employers evaluating portfolios from people they have never met — all arrive with reasonable skepticism.

Stripe users arrive trusting that digital payments are real. GitHub users arrive trusting that code repositories are real. UmojaHub users arrive in an environment where:

- Farmers have been exploited by middlemen who had information advantages
- Buyers have no external mechanism to confirm a farmer's reliability before transacting
- Students have portfolios that no employer can independently verify
- Employers have seen CV inflation, AI-generated work, and unverifiable GitHub contributions
- NGOs and government agencies need documented evidence before citing platform impact

The website exists because trust must be built before it can be used.

The web application cannot build this trust. It is optimized for people who have already decided to engage. The website is optimized for people who have not yet decided. These are different states of mind, requiring different information, different depth, and different emphasis.

---

## WHY THE WEB APPLICATION EXISTS

The web application exists for people who have passed through the trust-building phase and are ready to act.

By the time someone enters the application:
- They understand what UmojaHub is
- They understand what role they occupy within it
- They have decided the platform is relevant to them
- They need to accomplish something specific

The application is a work environment. Its job is execution, not explanation. A farmer opening the application wants to create a listing or check their orders — not re-read why verification exists. A student opening the application wants to submit their project document — not re-read what peer review involves. Every second the application spends explaining the platform is a second wasted for a person who already understands it.

---

## THE DIVISION

The website owns: **understanding**.
The web application owns: **action**.

These are not overlapping responsibilities. They are sequential stages in a single user journey. A person moves from website to web application exactly once per engagement with the platform. They do not oscillate between them. The website completes its job when the user registers. The web application begins its job the moment the user logs in.

This means:

The website must be complete enough that no one needs to return to it to answer a question once they are inside the application. If a user inside the application is confused about how the trust score works, that is a website failure — the website did not explain it sufficiently before registration. The fix is to improve the website, not to add explanatory text inside the application.

The web application must be focused enough that it contains no content a visitor without an account should read. If a researcher needs to understand how lecturer review works, they should find that explanation on the website. If the application is their only source for that information, the boundary has been violated.

## BOUNDARY RULES

**Rule 1 — The Publication Rule**
The website publishes. The application operates. Publishing means making information available to any reader, without authentication, without interaction, without consequence. Operating means creating records, changing state, moving money, or updating data.

**Rule 2 — The Anonymous Access Rule**
Everything on the website must be accessible to a visitor who will never create an account. This visitor may be a journalist, a researcher, an NGO analyst, a government official, or a potential user who never converts. The website serves them completely. If a piece of content requires a login to make sense, it belongs in the application.

**Rule 3 — The Irreversibility Rule**
The website never initiates any irreversible action. It cannot create records. It cannot trigger payments. It cannot modify data. Every interaction on the website is read-only from the platform's perspective. The user reads, evaluates, and decides — the website never acts on their behalf.

**Rule 4 — The Role Independence Rule**
The website does not know what role a visitor will eventually occupy. It serves farmers, students, buyers, employers, NGOs, researchers, and journalists from the same public surface. A page on the website may be organized for a specific audience, but it does not require the visitor to identify themselves to access it.

**Rule 5 — The Completion Rule**
The website's job is complete when a visitor can accurately describe the platform to someone else, understand whether it is relevant to them, and know what to do next. Every page, section, and paragraph is evaluated against this standard: does it move the visitor toward complete understanding, or is it noise?

**Rule 6 — The Accountability Rule**
The website makes the platform's governance visible. Who reviews verifications. What criteria govern decisions. How disputes are handled. How impact is measured. What the platform cannot do. This information belongs on the website because it serves people who will never create accounts (auditors, journalists, government) and because trust that requires authentication to be verified is not trust at all.

**Rule 7 — The Limitation Rule**
Every capability claim on the website is paired with an honest statement of what that capability does not cover. The platform verifies farmer identity — but not produce quality in advance. The platform records project verification — but does not guarantee employment outcomes. These limitations are not footnotes. They are primary content. A user who enters the platform with false expectations becomes a user who loses trust when reality diverges.

## CONTENT PRINCIPLES

**Principle 1 — Inform, never persuade.**
The website communicates facts. It does not sell. It does not use emotional language to generate excitement. A farmer reading the website should finish with an accurate picture of what the platform does and does not do — not an emotional desire to be part of something transformative. A user who joins because of accurate information is more likely to succeed on the platform than a user who joins because of a compelling pitch.

**Principle 2 — Depth over simplification.**
The website's audiences are making real decisions. Farmers are deciding whether to submit identity documents to a platform they found online. Students are deciding whether to invest hours of work into a verification system. Employers are deciding whether to trust a portfolio in a hiring context. These decisions deserve substantive information, not marketing summaries. If an explanation requires three paragraphs, write three paragraphs.

**Principle 3 — Precision over generality.**
Vague claims ("we help farmers earn more") are worse than no claim at all because they generate expectations the platform may not meet. Every claim is stated in terms of what the platform specifically does: "farmers can compare their listed price against verified weekly market benchmarks for ten major Kenyan crops." That claim is verifiable, limited, and honest.

**Principle 4 — Disclosure is trust.**
Stating what the platform does not do, cannot verify, or does not track is a stronger trust signal than any positive claim. The platform does not track post-transaction produce quality. The platform does not guarantee employment outcomes for students. The platform does not take a commission. These disclosures are content, not disclaimers. They are placed prominently alongside the capabilities they qualify, not buried in legal text.

**Principle 5 — Every section earns its place.**
A section on the website exists only if removing it would leave a visitor less informed. Content that exists to create visual interest, to fill space, to appear comprehensive, or to demonstrate effort is eliminated. The test: would a visitor who skipped this section make a worse decision about whether to use the platform? If no, the section is cut.

**Principle 6 — Completeness over rationing (the all-out standard).**
Every platform capability is explained in full: how it works, what it verifies, what it cannot guarantee, and the criteria that govern it. Information is never truncated for brevity, never withheld to manufacture a reason to register, and never split so that understanding requires assembling fragments scattered across the surface. A visitor must be able to reach total understanding of any single mechanic in one continuous, self-directed reading — without rationing their learning and without abandoning a topic half-explained. This principle does not override Principle 5: depth is unbounded only for content that earns its place. Completeness is the standard; length is not the goal. A section is as long as the truth requires and not one sentence longer.

**Principle 7 — Paired limitation.**
Every capability is immediately followed by an explicit statement of what it does not cover, positioned directly alongside the claim it qualifies — never in a footer, on a separate page, or in legal text. This makes Rule 7 structural: the limitation is part of the same reading unit as the capability, so no visitor can encounter a claim without also encountering its boundary.

**Principle 8 — Functional visuals carry evidentiary weight.**
Where live product screenshots are unavailable or insufficient, the website explains mechanics through diagrams, schematics, and flowcharts — the M-Pesa payment lifecycle, the trust-score calculation, the verification workflow, data flows. These visuals are held to the same standard as the text: they inform, they are accurate, and they are limited in scope. A visual that exists to decorate, to impress, or to suggest a sophistication the platform has not earned is cut under Principle 5 exactly as text would be.

## TRUST PRINCIPLES

**Trust principle 1 — Named accountability.**
Anonymous governance is not governance. The website discloses the names and credentials of the people who make verification decisions. Not because regulation requires it, but because a farmer submitting identity documents to an unnamed entity has no basis for trust. Names, roles, and decision criteria are public.

**Trust principle 2 — Methodology transparency.**
The trust score is not a black box. The four components, their weightings, and the events that trigger recalculation are explained on the website. A buyer who understands how a trust score is calculated can make an informed decision when comparing farmers. An explanation that demystifies the algorithm is more trustworthy than one that presents it as authoritative without explanation.

**Trust principle 3 — Process transparency.**
The verification process is explained in enough detail that a farmer knows exactly what will happen to their documents, who will review them, what criteria govern the decision, and what their options are if rejected. A student knows exactly what the reviewer will assess, on what dimensions, and what each possible outcome means. Process transparency removes the anxiety of the unknown.

**Trust principle 4 — Live evidence over claims.**
Real numbers from the platform — verified farmers, completed transactions, counties represented, student portfolios verified — are stronger trust signals than any assertion about the platform's value. These numbers are published publicly and updated regularly. If the platform is early and the numbers are small, the small numbers are published honestly. A platform that publishes small honest numbers is more trustworthy than one that publishes inflated claims.

**Trust principle 5 — Appeals and recourse.**
Every trust system must have a correction mechanism. The website explains what happens when a verification decision appears wrong, what the formal appeals process involves, who handles appeals, and what the timeline is. The existence of a real appeals process is itself a trust signal.

## COMMUNICATION PRINCIPLES

**Communication principle 1 — Write for the actual user, not the ideal user.**
The primary audiences of the website include farmers in Wajir accessing the internet on a mid-range Android phone with an intermittent connection. Students in Nairobi who are skeptical of any platform claiming to help their career. Employers who have seen credential inflation and are looking for reasons to distrust a portfolio. The website communicates in plain language that these people can parse in their actual conditions.

**Communication principle 2 — Answer the question being asked.**
Visitors arrive with specific questions. "What is UmojaHub?" "How does payment work?" "Who reviews my documents?" "What does Portfolio Verified mean?" The website is organized to answer these questions directly and completely, not to lead visitors through a designed narrative before reaching the answer.

**Communication principle 3 — Accuracy over persuasion.**
When a claim would be more persuasive if slightly overstated, it is stated accurately. When a limitation makes the platform appear less capable than a competitor, it is disclosed. The website's credibility is its primary asset. A single inaccurate claim discovered by a journalist or researcher damages trust more than any positive claim repairs it.

**Communication principle 4 — No aspirational language.**
The website does not use language about what the platform aspires to do, what it envisions, or what it is working toward. It describes what the platform does today. Future capabilities are not mentioned unless they are in active development with a committed timeline. "Transforming agriculture" and "empowering farmers" are replaced with specific, verifiable descriptions of what the platform specifically does.

## AUDIENCE DEFINITIONS

### Website Audiences

**Pre-registration Farmers**
Smallholder Kenyan farmers who have heard about UmojaHub through an extension officer, cooperative, or word of mouth. They need to understand: what the platform does for them specifically, what the verification process requires, what a trust score means, and what the platform cannot do for them. They make the decision to register or not based on what they find on the website.

**Pre-registration Buyers**
Individuals, households, restaurants, hotels, schools, and procurement entities who want to buy produce directly from verified farmers. They need to understand: how the marketplace works, how to interpret trust scores, how M-Pesa payment works, and what their recourse is if something goes wrong. They make the decision to register or not based on what they find.

**Pre-registration Students**
Kenyan computer science students evaluating whether the Education Hub is worth their time. They need to understand: what Portfolio Verified means, what the three-document structure involves, who reviews their work, what each outcome (VERIFIED, REVISION_REQUIRED, DENIED) means, and what limitations exist. This audience is analytically skeptical — they will read carefully.

**Employers (non-registering)**
Technology companies, startups, NGOs, and government agencies that hire software developers. They will never create an account. They access the website because a student sent them a portfolio link, or they are evaluating the verification system for hiring purposes. They need to understand: exactly what was verified, by whom, using what criteria, and how they can independently confirm it.

**NGOs and Development Organizations**
Organizations with food security, agricultural development, or youth employment mandates. They need to understand: the platform's mission alignment, its geographic reach, its impact metrics, what data it can and cannot provide, and how they can support farmer or student adoption. They may never register.

**Government Agencies**
National and county government agencies with agriculture, food security, youth employment, or ICT mandates. They need to understand the platform's verification methodology, geographic coverage, data governance, and partnership possibilities. They will not register.

**Academic Institutions**
Universities and polytechnics considering whether to encourage faculty and student participation. They need to understand how individual faculty verify as lecturers, how student participation works independently of institutional enrollment, and how the portfolio system relates to academic credentialing. They do not register as institutions.

**Researchers and Journalists**
People investigating the platform's claims, methodology, or impact. They need complete access to the platform's governance documentation, methodology disclosures, impact data, and accountability structures — without creating an account. The website must serve this audience completely.

**Auditors and Funders**
Donors, grant-making organizations, impact investors, and potential partners evaluating the platform for investment or partnership. They need the same access as researchers: complete governance, methodology, and impact documentation.

### Web Application Audiences

**Verified Farmers**
Farmers who have passed identity verification and are active on the platform. They use the application to create and manage listings, track orders, receive payment confirmations, monitor their trust score, access price intelligence, use the AI farm assistant, and manage cooperative group activity.

**Buyers**
Registered buyers placing orders and completing M-Pesa payments. They use the application to browse (this overlaps with the website), select produce, initiate payment, track fulfillment, confirm receipt, and submit ratings.

**Students**
Computer science students active in the Education Hub. They use the application to select a project track, receive their brief, submit three documents, complete peer reviews, receive lecturer decisions, and manage their portfolio.

**Lecturers**
Verified academic professionals using the application to access the review queue, select student projects for review, complete four-dimension assessments, and submit verification decisions.

**Platform Administrators**
The named individuals responsible for verification decisions. They use the application to access verification queues, review submitted documents, make approval or rejection decisions, and manage the supplier directory and knowledge base.

## INFORMATION OWNERSHIP RULES

These rules govern which system owns which information. "Owns" means: this system is the source of truth for this information, and this system is where the information must be found.

**The website owns:**
- What UmojaHub is and why it exists
- Who each audience is and what the platform does for them
- How verification works (process, criteria, timeline, outcomes)
- What trust scores are and how they are calculated
- What the three-document project structure involves and why
- Who the platform administrators are, what their credentials are, and what criteria govern their decisions
- What the appeals process is and how to initiate it
- What the platform's current operational metrics are (verified farmers, transactions, portfolios, counties)
- What the platform does not do, cannot verify, and does not track
- What third-party services are used and why
- How M-Pesa payment works from both sides of a transaction
- What the risks are for each audience and how they are mitigated
- What happens if something goes wrong for each audience

**The web application owns:**
- The authenticated user's current state (listings, orders, trust score, project status)
- The verification queue and individual review decisions
- Active project workspaces and document submissions
- Order history and payment status
- Peer review assignments and submission forms
- Price intelligence data for the authenticated farmer's context
- AI assistant and mentor conversations
- Account settings, profile management, and document upload
- Notification history

**Neither owns (platform infrastructure):**
- The marketplace listing browse — this is a platform surface accessible from the website context but not owned by either system as pure website or pure app. Anonymous visitors browse it from the website. Authenticated buyers use it to initiate purchases from the web app. The browse experience belongs on the website. The purchase action belongs in the web app.
- The knowledge hub — same logic. Public reading belongs on the website. Administrative management belongs in the web app.
